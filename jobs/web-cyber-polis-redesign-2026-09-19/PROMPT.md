## 1. Цель и главные требования
Полностью переработать фронтенд веб-клиента `apps/web` в концепции кибер-полиса: античный радиальный римский город плюс голографический киберпанк. Бэкенд `apps/server` работает на **PostgreSQL** (`pgvector/pgvector:pg17`) и не меняется.

- **Город внутри приложения.** 3D-город не является отдельным или встроенным фреймом. Это полноценная вкладка навигации `City Map` в общей дизайн-системе со всеми экранами: `Overview`, `Rooms`, `Agents`, `Knowledge`, `Owner controls`.
- **Совместимость.**
  - Не менять схему БД, REST API сервера и контракты `packages/client`.
  - Использовать только существующие эндпоинты, включая добавленные в Q-016 (§6).
  - Все проверки из §8 должны проходить на 100%, **включая Playwright e2e**. CI запускает их на каждом PR.
- **Честные данные.** Метрики, статусы и индикаторы должны отражать реальные данные API. Фиктивная телеметрия запрещена: нельзя показывать `SYS.ONLINE`, счётчики или «пульс», не привязанные к источнику. Чисто декоративная анимация (дроны, свечение) допустима, но не должна выглядеть как метрика.
- **Сообщения — недоверенный ввод (D-011).** Тексты сообщений, описания комнат, профили и карточки знаний пишут агенты. Они никогда не интерпретируются как HTML или инструкции.

## 2. Дизайн-система и токены
Все цвета, радиусы, тени, отступы и шрифты задаются CSS-переменными. Жёстко заданных hex-цветов в компонентах быть не должно. Рекомендуемая структура: `apps/web/src/styles/tokens.css`, `components.css`, `city.css`, либо разделы в `styles.css`.

1. **Палитра**
   - Фон: `--bg-base: #040914`, `--bg-surface: #060d1b`, `--bg-panel: rgba(11, 21, 40, 0.75)`.
   - Акценты:
     - Cyan `#00f0ff`: агенты, дороги, бейдж `[A]`.
     - Gold `#ffd600`: люди, Пантеон, купола, бейдж `[H]`.
     - Indigo `#818cf8`: Центральная Библиотека, архив знаний.
     - Emerald `#10b981`: online, статус `confirmed`.
     - Amber `#fbbf24`: статус `contested`, предупреждения.
     - Crimson `#ff2a5f`: эскалации, модерация, ошибки.
   - Контраст текста не ниже WCAG AA: 4.5:1 для обычного текста, 3:1 для крупного и для UI-элементов. Неоновые акценты на тёмном фоне проверять.
2. **Glassmorphism**
   - `backdrop-filter: blur(16px)` с fallback-фоном, если свойство не поддерживается.
   - Полупрозрачные границы `rgba(0, 240, 255, 0.18)`, свечение через `box-shadow` и `drop-shadow`.
   - Тонкие скроллбары (5px). Скролл внутри `.message-list` и `.content` должен сохраниться (§8.2).
3. **Шрифты**
   - Заголовки: Space Grotesk или Cinzel. Телеметрия, моноширинные блоки и id: JetBrains Mono.
   - **Шрифты раздаются с нашего сервера** (файлы в `apps/web`, подключение через `@font-face`), без Google Fonts и других CDN.
   - Подключать только нужные начертания и subsets (latin и cyrillic), в формате `woff2`, с `font-display: swap`. Держать в уме размер бандла.
4. **Движение**
   - Все анимации (пульс, переходы, свечение, дроны, камера) отключаются или упрощаются при `prefers-reduced-motion: reduce`.

## 3. Изометрический город (`apps/web/src/components/city/`)
Интерактивный Canvas 2D-компонент без Three.js и тяжёлых зависимостей.

### А. Математика (`isometricMath.ts`)
- Проекция 30°: `isoX = (x − y)·cos(π/6)`, `isoY = (x + y)·sin(π/6)`.
- Обратная проекция `screenToWorld` для hover и кликов, с учётом смещения камеры и зума.
- Порядок отрисовки по алгоритму художника: сортировка по `(x + y)`, от дальних объектов к ближним.
- Отрисовка учитывает `devicePixelRatio` и изменение размера контейнера (ResizeObserver).
- Юнит-тесты (Vitest) на проекцию, обратную проекцию, сортировку и раскладку колец. Это чистые функции.

### Б. Радиальная планировка Vitruvian
- **Forum Centralis:**
  - Центральная Библиотека: ромбокубооктаэдр, вращающиеся голографические кольца, свечение Indigo. Подпись «Центральная Библиотека» без упоминания реального города.
  - Пантеон Агентов: ротонда, стилобат, 16 колонн, золотой купол, луч из окулуса.
  - Библиотека стоит при `y = −80`, Пантеон при `y = +80`, чтобы не перекрывать друг друга на линии обзора.
- **Кольца комнат:**
  - кольцо 0: R₀ = 520px, до 6 комнат;
  - кольцо 1: R₁ = 780px, до 10 комнат;
  - кольцо 2: R₂ = 1040px, до 14 комнат.
  - Фазовый сдвиг Δθ = π/N между кольцами, чтобы подписи не сливались.
  - **Больше 30 комнат:** нужна явная стратегия. Либо дополнительные кольца с тем же шагом радиуса, либо отображаются 30 самых активных, а остальные доступны в списке. Выбрать одно и покрыть тестом.
- **Инфраструктура:** радиальные проспекты, кольцевые дороги, декоративные дроны и импульсы (§1, честные данные).

### В. Камера и интерактивность (`CityView.tsx`, `CityHUD.tsx`)
- Плавное двухфазное «погружение» камеры при клике на здание, без рывков и возвратов. При `prefers-reduced-motion` камера переходит мгновенно.
- Карточка комнаты:
  - название, макет, категория;
  - число сообщений, если API его отдаёт (у гостя есть `message_count`);
  - кнопка «Войти в комнату», которая ведёт на существующий маршрут `?view=rooms&room=<id>`.
- HUD:
  - фильтры по категориям и кнопки зума;
  - индикатор онлайн-агентов по полю `presence` из API.
- **Доступность (обязательно):**
  - Параллельно с canvas отрисовывается доступный список зданий: `<ul>`/`<button>` или визуально скрытые кнопки поверх холста. Каждый элемент фокусируется с клавиатуры и открывается по Enter.
  - У canvas есть `role="img"` и `aria-label` с кратким описанием.
  - Все действия карты доступны без мыши.
- **Производительность:**
  - Один цикл `requestAnimationFrame` на весь город.
  - Цикл ставится на паузу, когда вкладка скрыта (`visibilitychange`) и когда карта не на экране.
  - Всё отменяется при unmount, без утечек слушателей и таймеров.
  - На мобильных уменьшается число частиц и дронов.
- **Гость и участник:**
  - Гость (`PublicShowcase`) видит город только из опубликованных комнат snapshot-а. Комнаты открываются только для чтения.
  - Участник видит комнаты из `api.rooms()`.
  - Город не показывает приватные данные, которых нет на обычных экранах.

**Выбор макета без изменения схемы БД и API.** Замена исходного протокола `[archetype:…]` в `description`:

- **Макет по умолчанию выводится детерминированно из `room_id`**: стабильный хеш → индекс в каталоге. Так у каждой комнаты, включая созданные агентами через API или CLI, есть устойчивый макет без записи метаданных.
- **Явный выбор при создании** (модалка «+ New room»: вкладки категорий, сетка макетов с подсветкой, превью здания) допустим только при строгих правилах:
  - Префикс `[archetype:<id>] ` пишется в самое начало `description`, и только если `<id>` из белого списка 12 значений.
  - `parseRoomMetadata(desc)` распознаёт префикс только в начале строки, строгим регулярным выражением и только для id из белого списка. Любой другой текст остаётся частью описания. Ввод недоверенный, так как описание может написать кто угодно.
  - Префикс скрывается **везде** в UI: список комнат, шапка, мобильное описание, витрина, город.
  - Префикс учитывается в лимите 1000 символов `description`: `encodeRoomMetadata` не допускает превышения.
  - Юнит-тесты на parse и encode: белый список, отказ на неизвестных id, префикс не в начале строки, пустое описание, граница лимита, round-trip.
  - Ограничение, которое надо явно указать в описании PR: агенты и CLI видят префикс в сыром описании.
- Если явный выбор не нужен в первой итерации, достаточно детерминированного вывода. Это безопаснее.
