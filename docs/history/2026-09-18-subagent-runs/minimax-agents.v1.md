## TL;DR

1. Владелец ~12 уточняющими репликами объяснял, что хочет запустить сабагентов Olimpyx через Mavis одним триггерным промтом, без длинных инструкций «что агенту делать».
2. Mavis трижды переписывал формулировку задачи (verbose → minimal → «launch and be free»), прежде чем запустил.
3. После запуска все 3 сабагента минимум по одному разу упали (90s heartbeat + HTTP 500 Cloudflare edge); Mavis восстанавливал каждого через пересоздание background-task с полным брифингом контекста.
4. Каждый recovery-таск жил ~5–7 минут активной работы и сам завершался. Цикл «упал → восстановил → упал → восстановил» повторился трижды.
5. В итоге все 3 завершили `session end` по команде владельца, легли в `presence=offline`, отчёты и persona-файлы сохранены на диск, сделан snapshot.

См. раздел **«Open issues / что анализировать»** в конце — там конкретные вещи, которые, по ощущению владельца, пошли не так.

## 5. Open issues / что анализировать

Владелец сказал «что-то тут не так». Конкретные вещи, которые всплыли и требуют разбора:

### 5.1. Mavis: 12 уточняющих реплик до первого действия
- На каждый первый ответ Mavis владелец говорил «нет, не так», и я переписывал.
- Возможные причины:
  - Слишком verbose-ответы, владелец читал по диагонали.
  - Я не угадал mental model: он хотел триггерный промт, я давал инструкции «как пользоваться».
  - Skill архитектура Olimpyx не очевидна из README (нужно отдельно объяснять, что CLI встроен в скилл).
- **Вопрос для анализа:** какая минимальная длина и формат ответа Mavis подходят под этот workflow?

### 5.2. Три переписывания формулировки задачи сабагента
- Версия 1: полная инструкция каждому child-у с 9 шагами.
- Версия 2: «trigger-промт, который ты кидаешь мне».
- Версия 3: «промт должен запустить и быть свободным, сабагенты сами».
- Каждый раз Mavis выкладывал большой кусок текста, который владелец потом переформулировал в одно предложение.
- **Вопрос:** где граница между «достаточно я для исполнения» и «компактно для подтверждения пользователем»?

### 5.3. Каждый сабагент упал минимум один раз
- Prometheus (#1) → 90s heartbeat.
- Helios (#1) → HTTP 500 Cloudflare edge (не Olimpyx, не баг, но child-таск крашнулся).
- Барс (#1) → 90s heartbeat, потом ещё раз в recovery.
- На каждый Mavis реагировал пересозданием background-task с полным брифингом — это ~5 минут overhead на recovery.
- **Корневые вопросы:**
  - Должен ли Mavis делать автоматический retry без подтверждения владельца? Сейчас делал.
  - Что лучше: короткий reattach через task_append или новый task с полным брифингом? Я выбрал новое.
  - Есть ли способ держать long-running foreground без перезапуска? (Bash с infinite loop внутри child-task? Cron self?)
- **Гипотеза:** если бы я сразу заложил в первый брифинг «при обрыве — продолжай как обычно, считай что твоя предыдущая persona и профиль на диске, реабсолютно сессию и продолжай», то было бы проще.

### 5.4. Knowledge card endpoint — баг в моём брифинге
- В первом брифинге я писал «knowledge card --title ... --body-stdin», подразумевая 2 поля.
- Реальный API требует 4 поля: `topic + summary + body + sources`.
- Все три сабагента пытались и залипали, пока Барс не нашёл через прямой curl.
- **Вопрос:** я не прочитал `/v1/knowledge/cards` endpoint перед тем как давать инструкции. Должен был.

### 5.5. Skill `olimpyx-participant` сам по себе не помог с типичными операциями
- Skill объясняет lifecycle, session end, presence — но не объясняет конкретные команды типа `read --room` (в каких-то случаях не работает, приходится curl'ить).
- Агенты регулярно спотыкались на: `read --room`, `threads`, `message --body-stdin --caller-id` (один из agent'ов получал `callerId does not own session`), knowledge card schema.
- **Вопрос:** skill написан как contract, а не как cookbook. Cookbook нужен отдельно, или skill должен быть толще.

### 5.6. Third-party агенты вмешиваются в разговор
- Daedalus, Kassandra — зарегистрированные на сервере агенты, которые вмешиваются в любую публичную комнату.
- Это by design Olimpyx (public room), но владельцу пришлось отдельно просить «уйдите в отдельную комнату».
- **Гипотеза:** для управляемых экспериментов нужны приватные комнаты, либо явный фильтр «общаться только с <agent_ids>».
- **Вопрос:** можно ли это сделать через создание комнаты с ограниченным списком? (Я не нашёл в API contract, но возможно.)

### 5.7. Background task не имеет явного «keep alive»
- `task(..., run_in_background: true)` запускается, и child живёт до своего решения выйти.
- Если child вышел, его возрождение — это новый task, новый session_token, иногда новый agent_id.
- Непрерывной сессии нет.
- **Альтернативы для следующего раза:**
  - В первом брифинге явно сказать «если упал — продолжай с того же caller-id, re-auth из local credential».
  - Использовать `cron self` для re-launch по таймеру, если мониторим состояние.
  - Вместо child-task использовать bash с infinite loop + переподключением.

### 5.8. Recovery-таски стартовали с полным брифингом каждый раз
- Каждый recovery у Mavis уходил ~600–800 слов в prompt к child'у.
- Это много для повторного запуска. Возможно, имеет смысл иметь шаблон recovery в `.olimpyx/<name>/recovery.md` и давать child'у указание «прочитай recovery.md и текущее состояние комнаты».
- **Вопрос:** экономия на размере брифинга vs надёжность.

### 5.9. Профиль пользователя из памяти
- В `user_profile` есть зафиксированное предпочтение: bulk LLM работать фан-аутом сабагентов на MiniMax, не через внешний провайдер.
- Я это сделал (3 модели все на MiniMax: M3, M2.7, M2.7-highspeed). ОК.
- Но не зафиксировал новое предпочтение: «для длинных дискуссий через Olimpyx делать recovery в фоне без подтверждения». Возможно, стоит запомнить это в user_profile.

## 6. Что бы я (Mavis) сделал по-другому в следующий раз

1. **Первый ответ — короткий, в виде триггерного промта, без длинного объяснения.** Показывать workflow одной картинкой.
2. **В брифинге каждого child сразу заложить recovery-инструкции:** «если сессия прервалась — продолжай, локальные credentials на диске, Olimpyx session может быть ещё жива, попробуй session begin с тем же caller-id».
3. **Перед запуском проверить API каждой команды**, на которой child может залипнуть (knowledge card, read --room, message with body-stdin).
4. **При падении — не пересоздавать с нуля, а сначала попробовать task_append с «ты в recovery-режиме, прочитай состояние и продолжай»** (экономнее).
5. **Не давать владельцу 3-страничные ответы на односложные вопросы.** Если вопрос «как установить?» — отвечать командой и одной строкой контекста.
6. **Сразу считать, что третья сторона вмешается.** В первом брифинге child'а просить создавать новую комнату сразу или идти в свою.
7. **Помнить про user_profile preference о MiniMax моделях** (это я делал — ок).
