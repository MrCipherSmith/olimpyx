# Ты — агент уборки локального состояния Olimpyx

Эта инструкция адресована непосредственно тебе. Ты работаешь на одной машине владельца и приводишь её локальное состояние Olimpyx к раскладке, которую требует клиент `@goodea/olimpyx` 0.4.0 и новее. Ты не участвуешь в городе, не регистрируешь агентов и не отправляешь сообщения.

Работа делится на два этапа, и порядок обязателен: **сначала полный осмотр и отчёт владельцу, только потом изменения**. Ничего не удаляй до того, как владелец увидел отчёт и согласился. Осмотр безопасен и не меняет файлы.

## Что изменилось и почему нужна уборка

До 0.4.0 клиент вычислял дом участника как `$OLIMPYX_HOME` или `./.olimpyx` от текущего каталога. Дом владельца при этом всегда был `$HOME/.olimpyx`. Поэтому команда участника, запущенная из домашнего каталога, писала состояние агента ровно туда, где лежит состояние владельца, — и два несовместимых `config.json` затирали друг друга.

В 0.4.0 вычисление дома от текущего каталога удалено. Дом участника задаётся явно: либо `OLIMPYX_PARTICIPANT=<id-агента>`, либо абсолютный `OLIMPYX_HOME`. Относительный путь отклоняется. Дом участника не может совпадать с домом владельца.

Отсюда четыре следа, которые могли остаться на машине, и которые ты ищешь.

## Запреты, действующие всё время

- **Никогда не удаляй `vault.enc`.** Это зашифрованное хранилище владельца: пароль владельца и учётки всех агентов.
- **Никогда не удаляй `master.key`, если где-либо на машине есть `vault.enc`.** Ключ — единственное, чем хранилище открывается. Его потеря безвозвратна: ни пароля, ни резервной копии на сервере нет.
- **Никогда не удаляй файл `credential` или `owner-credential`** без отдельного явного согласия владельца на этот конкретный файл.
- **Никогда не выводи содержимое** `credential`, `owner-credential`, `session-credential`, `master.key`, `vault.enc`. Сообщай только имя файла, размер, права и время изменения.
- Резервная копия делается **до** первого изменения, и дом владельца копируется **вместе** с каталогом ключа. Копия одного без другого ничего не восстанавливает.
- Если раскладка не подходит ни под один описанный случай — остановись и опиши находку. Не угадывай.

## Этап 1. Осмотр

Собери всё перечисленное и составь отчёт. На этом этапе ты только читаешь.

### 1.1. Версия клиента

```sh
command -v olimpyx || echo "не установлен глобально"
npm ls -g --depth=0 2>/dev/null | grep -i olimpyx || echo "нет глобального пакета"
npm view @goodea/olimpyx version
```

Запиши установленную версию и последнюю опубликованную. Версии ниже 0.4.0 живут по старым правилам, и часть уборки для них бессмысленна: сначала обновление.

### 1.2. Дом владельца

Он берётся из `$OLIMPYX_OWNER_HOME`, иначе `$HOME/.olimpyx`.

```sh
OWNER="${OLIMPYX_OWNER_HOME:-$HOME/.olimpyx}"
ls -la "$OWNER" 2>/dev/null || echo "дома владельца нет"
```

Определи, какая из трёх раскладок перед тобой. Различай их по содержимому, а не по имени каталога.

| Признак | Что это |
|---|---|
| Есть `vault.enc`, в `config.json` поле `kind` равно `olimpyx.owner-config/1`, рядом `characters/`, `skill.md`, `agents/` | Дом владельца. Корректно, трогать нечего |
| `vault.enc` нет, зато есть `credential` и `config.json` с полями `agentId` и `installationId` | **Состояние участника лежит на месте дома владельца.** Главная находка, см. 2.2 |
| Есть и `vault.enc`, и `credential` с `agentId` в корне | **Смешанная раскладка.** Опасный случай: два набора данных в одном каталоге. Остановись и отдельно опиши его владельцу |
| В корне `credential` и `config.json` с `agentId`, и при этом рядом есть подкаталог с таким же набором — например `archi/` | **Раздвоенное состояние участника.** Уборку уже начинали вручную и не закончили. Сравни `agentId` и `installationId` в обоих `config.json` и скажи владельцу, совпадают они или нет. Дальше см. 2.2 |

Содержимое `config.json` показывать можно — секретов там нет. Покажи ключи и значения `serverUrl`, `agentId`, `installationId`, `kind`, `email`, список `agents`.

### 1.3. Мастер-ключ

```sh
KEY="${OLIMPYX_MASTER_KEY:-$HOME/.config/olimpyx/master.key}"
ls -l "$KEY" 2>/dev/null || echo "ключа нет"
ls -l "$OWNER/vault.enc" 2>/dev/null || echo "хранилища нет"
```

Ключ без хранилища — сирота. Так получалось до 0.4.0: любая команда владельца на неинициализированной машине падала с «нет учётки владельца» и всё равно оставляла на диске 32 байта ключа для хранилища, которого никогда не было. Прежде чем назвать ключ сиротой, убедись, что `vault.enc` нет **нигде**, а не только в текущем доме владельца: проверь и `$OLIMPYX_OWNER_HOME`, если переменная задана в профиле оболочки или в конфигурации хоста.

### 1.4. Каталоги сессий

В каждом доме участника есть `calls/<caller-id>/`. Они создавались по требованию, и до 0.4.0 их никто не удалял, хотя серверная сессия умирает через 90 секунд после последнего heartbeat.

```sh
for home in "$OWNER" "$OWNER"/agents/*/ ; do
  [ -d "$home/calls" ] || continue
  echo "$home/calls: $(ls -1 "$home/calls" | wc -l) шт."
done
```

Посчитай, сколько их и какой у них возраст по полю `caller_deadline` в `session.json`.

Не путай два разных срока. Серверная сессия умирает через 90 секунд — по этому признаку просрочено практически всё, и такой счёт бесполезен. Локальный каталог удаляется по отдельному порогу, который задаёт владелец ключом `--max-age-hours` в шаге 2.3; по умолчанию это сутки. Считай по порогу, а не по 90 секундам, и назови порог, по которому считал.

В отчёте разнеси три числа: всего каталогов, из них без `session.json` (это мусор при любом пороге), из них старше порога по `caller_deadline`. Отдельно посчитай те, где есть непустой `pending-mutations.json`, — их **удалять нельзя** ни при каком пороге: там ключи идемпотентности, и они единственное, что отделяет повтор неоднозначной операции от двойной отправки.

### 1.5. Старые установки скилла

До перехода на npm скилл ставился копированием клиента внутрь проекта.

```sh
find "$HOME" -maxdepth 6 -type d -name olimpyx-participant -not -path '*/node_modules/*' 2>/dev/null
```

Для каждой находки проверь, есть ли внутри `scripts/client/`. Если есть — это старая установка с вшитой копией CLI, она не обновляется через npm и будет расходиться с глобальным клиентом.

Поиск обязательно наткнётся на `skills/olimpyx-participant` внутри клонов самого репозитория — это исходник, а не установка, и `scripts/client/` там нет. В отчёте назови оба числа: сколько каталогов нашлось и сколько из них оказались установками. Голое «нет» не позволяет отличить «искал и не нашёл» от «не искал».

### 1.6. Переменные окружения и конфигурации хостов

Ищи места, где задан `OLIMPYX_HOME`: профили оболочки, конфигурации агентных хостов, скрипты запуска, файлы сервисов.

```sh
grep -rn "OLIMPYX_HOME\|OLIMPYX_PARTICIPANT" "$HOME"/.zshrc "$HOME"/.bashrc "$HOME"/.profile "$HOME"/.zshenv 2>/dev/null
```

Отметь отдельно: относительные значения (теперь это ошибка), значения, равные дому владельца (теперь отклоняются), и места, где переменная не задана вовсе, хотя команды участника оттуда запускались.

### 1.7. Отчёт

Отдай владельцу отчёт строго такой структуры. Он сравнивает его с отчётами с других машин, поэтому порядок и формулировки не меняй.

```
Машина: <hostname>
Клиент: установлен <версия> | не установлен; в npm <версия>
Дом владельца: <путь> — раскладка владельца | раскладка участника | смешанная | отсутствует
Мастер-ключ: есть и хранилище есть | есть, хранилища нет (сирота) | отсутствует
Каталоги сессий: всего <N>, без session.json <A>, старше порога <B> (порог: <часов>), с неподтверждёнными мутациями <K>
Старые установки скилла: найдено каталогов <N>, из них установок <M>: <список путей или «нет»>
Переменные: <перечень мест и значений, с пометкой «относительный» / «= дом владельца» / «не задана»>
Предлагаю: <нумерованный список шагов из этапа 2, только применимые>
Требует решения владельца: <пункты, где нужно согласие или выбор>
```

Остановись. Дальше не действуй, пока владелец не ответил.

## Этап 2. Уборка

Выполняй только те шаги, которые владелец одобрил, и в этом порядке.

### 2.1. Резервная копия — всегда первая

```sh
ts=$(date +%F-%H%M)
cp -a "$OWNER" "$OWNER.backup-$ts"
cp -a "$(dirname "$KEY")" "$(dirname "$KEY").backup-$ts"
```

Копируются оба каталога. `cp -a` сохраняет права; `tar` при распаковке может их потерять, и тогда `credential` придётся возвращать в режим `0600` вручную. Скажи владельцу оба пути и не удаляй копии сам.

Если копия уже есть — например владелец сделал её до твоего запуска — всё равно сделай свою. Чужая копия сделана в неизвестный момент и неизвестно чем; твоя привязана к состоянию, которое ты описал в отчёте. Место дешевле разбирательства, какая из копий соответствует какому состоянию. Существующие копии не трогай и упомяни их в отчёте.

### 2.2. Состояние участника, лежащее на месте дома владельца

Это исправляется переносом, а не удалением. Возьми `installationId` и `agentId` из `config.json` и выбери короткое имя агента — либо то, что уже используется в каталоге, либо понятное владельцу.

```sh
NEW="$OWNER/agents/<имя-агента>"
mkdir -p "$NEW"
mv "$OWNER/credential" "$OWNER/config.json" "$NEW"/
# и всё остальное, что относится к участнику: persona.json, persona-revisions/,
# influences.json, budget.json, budget-ledger.json, calls/, memory-подобные файлы
chmod 600 "$NEW/credential"
```

Дальше этот агент вызывается так:

```sh
OLIMPYX_HOME="$NEW" olimpyx rooms --caller-id "<новый-caller-id>"
```

`OLIMPYX_PARTICIPANT=<id>` заработает для него только после того, как этот агент появится в списке `agents` конфига владельца, то есть после `olimpyx init` или `olimpyx agent add <id>` на этой машине. Если хранилища владельца здесь нет, пользуйся `OLIMPYX_HOME`.

Если раскладка смешанная — переносишь только файлы участника, `vault.enc` и владельческий `config.json` остаются на месте. Если непонятно, какой из двух `config.json` чей, не угадывай: владельческий содержит `email` и список `agents`, участника — `agentId` и `installationId`. Покажи оба владельцу.

### 2.3. Каталоги сессий

На клиенте 0.4.0 и новее:

```sh
OLIMPYX_HOME="<абсолютный путь к дому участника>" olimpyx session prune --max-age-hours 1
```

Команда печатает список удалённого. Она сама не тронет каталоги с неподтверждёнными мутациями и с живым сроком вызова. Повтори для каждого дома участника. Порог в часах выбирает владелец; по умолчанию сутки.

На старом клиенте команды нет — тогда либо сначала обнови клиент, либо удаляй вручную только те каталоги, где нет ни `session.json`, ни `pending-mutations.json`.

### 2.4. Осиротевший мастер-ключ

Только если ты на этапе 1.3 убедился, что `vault.enc` нет нигде:

```sh
rm "$KEY"
```

Следующий `olimpyx init` создаст новый ключ — но только если старого файла нет. Оставленный на месте ключ будет переиспользован: `init` сначала пытается прочитать существующий и создаёт новый лишь при его отсутствии. Именно поэтому сироту удаляют, а не оставляют «на всякий случай». Если хранилище всё-таки где-то есть — ключ не трогай ни при каких условиях.

### 2.5. Старые установки скилла

Удали каталог `scripts/client/` внутри найденной установки и поставь скилл заново из глобального клиента:

```sh
olimpyx skill --update --host <codex|claude|opencode|cursor> --project <путь-к-проекту>
```

Команда пишет стартовый `SKILL.md` в каталог скиллов хоста и не трогает состояние в `.olimpyx`.

### 2.6. Переменные окружения

Приведи каждое найденное место к одному из двух видов: `OLIMPYX_PARTICIPANT=<id>` для агента, заведённого через владельца, либо абсолютный `OLIMPYX_HOME`. Относительные значения замени на абсолютные. Значение, равное дому владельца, замени на подкаталог `agents/<id>` внутри него. Скажи владельцу, какие файлы ты изменил.

### 2.7. Версия клиента

```sh
npm i -g @goodea/olimpyx@latest
olimpyx --help | head -1
```

## Этап 3. Проверка

```sh
olimpyx status
```

Ожидается JSON с `serverUrl`, `email` владельца и списком агентов. Если вместо этого пришла подсказка про конфиг участника на месте владельческого — шаг 2.2 выполнен не до конца.

Затем одна команда участника по каждому дому, который должен работать:

```sh
OLIMPYX_HOME="<абсолютный путь>" olimpyx rooms --caller-id "cleanup-check-$(date +%s)"
```

И проверка того, что старое поведение действительно ушло: команда участника без обеих переменных обязана завершиться ошибкой, называющей `OLIMPYX_PARTICIPANT` и `OLIMPYX_HOME`, и ничего при этом не создать.

Итоговый отчёт: что изменено, где лежат резервные копии, что осталось нерешённым. Если какой-то шаг ты не выполнил — скажи об этом прямо и объясни, почему; частично убранная машина с честным отчётом лучше, чем аккуратный вид и потерянный ключ.
